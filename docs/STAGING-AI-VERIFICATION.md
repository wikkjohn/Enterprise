# Verifying a real AI provider in staging

`pnpm verify:ai` runs the release checks for a real provider against a staging
database. It creates a dedicated **staging organization** (`ai-staging-<id>`,
environment `staging`), configures an organization-owned Anthropic provider in
it (`anthropic-staging`, credential in the secret store), pins the org to that
provider with an enforced AI Ops routing policy, and drives the real platform
services, the real Anthropic adapter and the official SDK. Every request and
response that crosses the wire is captured and checked.

| Check | What it proves |
|---|---|
| **Grounded and cited** | Knowledge answers are generated by the provider. They contain the sourced facts, and every `[S#]` they cite is a retrieved passage. Every claim verifies against the sources, and no figure appears that the sources don't contain, even for a bait question the sources can't answer. Nothing retrieved means no provider call. An Engineering user's prompt never contains HR-only content; an HR user, as the control, does get it. |
| **Costs match** | For every billed request: recorded tokens = provider-reported `usage`. The served model (fallbacks included) is the one priced. Recorded cost = tokens × contract price, and `usage_events` agree. Every successful provider response maps to exactly one run (nothing unmetered). Org totals agree across the run log, the metering and the provider. Prompt-cache tokens are flagged, because the metering doesn't price them. |
| **Redaction** | An SSN and a card number are redacted: neither raw value, in any formatting, appears in any provider request, but the masked form does. An AWS key is blocked and a payroll export is held for approval, and neither causes a provider call. An SSN inside a knowledge document is stripped before the passage reaches the model. With full prompt retention, no raw value is stored in `ai_runs`. |
| **Fails closed** | An enforced policy that no model satisfies (provider not allowed, or a missing capability) returns `NOT_CONFIGURED`. That means HTTP 501, a fixed message, not retryable, and no stack or credential in the response. There is no provider call, no run and no cost. Other tasks keep working, and Knowledge degrades to a cited extractive answer that says why. |

## Run it

```bash
# 1. Point at the staging database and secrets (never production; the script refuses APP_ENV=production).
export DATABASE_URL=… APP_SECRET=… SECRETS_PROVIDER=… APP_ENV=staging
pnpm db:migrate

# 2. Live run. Use a dedicated staging API key so its usage is attributable.
ANTHROPIC_API_KEY=sk-ant-… pnpm verify:ai --live [--prices prices.json] [--out dir]

# 3. About five minutes later, reconcile with Anthropic's own usage records (Admin API key).
ANTHROPIC_ADMIN_KEY=sk-ant-admin-… ANTHROPIC_RECONCILE_API_KEY_ID=apikey_… \
  pnpm verify:ai --reconcile staging-verification/<run>/report.json
```

A live run makes about 15 short Claude API calls across Haiku 4.5, Sonnet 5.5
and Opus 5.5, costing a few cents. Results go to
`staging-verification/<timestamp>/`:

- `report.md` for people;
- `report.json` for machines and `--reconcile`;
- `costs.csv`: one row per request, with the provider `request-id`, served model, provider vs recorded tokens, and expected vs recorded vs metered cost.

The exit code is 0 only when every check passes.

**Contract prices.** Without `--prices`, costs are checked against the catalog
list prices. If your contract differs, pass
`{"claude-opus-5-5": {"input": 4, "output": 20}, …}` (USD per 1M tokens). The
staging models are configured with the same prices.

**Invoice.** The `--reconcile` step compares per-model token totals with
`/v1/organizations/usage_report/messages` for the run's window. The totals
match exactly only when the key carried no other traffic, so scope it with
`ANTHROPIC_RECONCILE_API_KEY_ID`. To compare with the invoice itself, filter
the Claude Console usage and cost views to the staging key and window. The
totals should equal the "Cost by model" table.

**Without a key.** `pnpm verify:ai --mock` runs the same harness against a
local Messages-API stand-in. `tests/integration/staging-verification.test.ts`
does the same in CI and injects faults (ungrounded answers, unpriced cache
tokens, fallback serving, DLP out of the path) to prove each check catches its
failure.

Each run leaves its staging organization in place for inspection. Suspend or
delete it from the platform admin when you're done.
